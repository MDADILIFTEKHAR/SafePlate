# SafePlate — Security & Privacy Architecture

SafePlate is engineered with privacy-by-design and rigorous security hygiene.

---

## 1. Local-First Privacy Guarantee

1. **Zero Cloud Exfiltration**: Food allergies represent personal medical data. SafePlate never sends user allergy profiles, medical history, or pantry inventories to third-party cloud AI vendors.
2. **Local AI Execution**: Open-weight inference runs on the user's host machine via **Ollama** or the local deterministic rule engine.
3. **No External Tracking**: No telemetry, analytics trackers, or third-party cookies are included.

---

## 2. Input Sanitization & Injection Defense

1. **SQL Injection**: All database operations use SQLAlchemy 2.0 ORM with strictly parameterized queries and bound variables. No raw unescaped SQL strings are executed.
2. **LLM Output Sandboxing**: SafePlate **never** executes code, scripts, or shell commands generated by an LLM. Model responses are parsed purely as declarative JSON data into strict Pydantic schemas.
3. **Input Validation**: All endpoints enforce schema bounds (e.g. positive budget amounts, non-empty names, trimmed and normalized allergy strings).
4. **Punctuation & Unicode Normalization**: Queries undergo normalization and regex boundary checks to prevent delimiter injection attacks.

---

## 3. Error Handling & Information Disclosure

1. **Sanitized Public Responses**: Internal database exceptions and system tracebacks are logged strictly to local server consoles for developer inspection.
2. **Generic User Error States**: Clients receive structured, user-friendly error objects (`"Something went wrong while generating your meal"`), preventing schema leaks or sensitive directory disclosure.
3. **Health Check Hygiene**: The `/health` endpoint exposes high-level service availability flags (`ok`, `degraded`) and model identifiers, without leaking system environment variables or file paths.

---

## 4. Rate & Resource Protection

1. **Concurrency Mutex**: An `asyncio.Lock()` enforces a single active meal plan generation per session, preventing accidental resource exhaustion if a user repeatedly clicks the generate action.
2. **Bounded Execution**: The agent iteration loop enforces `MAX_AGENT_ITERATIONS = 3` and `MAX_SUBSTITUTION_ATTEMPTS = 3`, preventing infinite retry loops or runaway CPU consumption.
3. **HTTP Timeouts**: All outbound LLM requests enforce explicit timeouts (`LLM_TIMEOUT_SECONDS = 30`), protecting the backend event loop from hanging processes.
